## 1. Qual è l'elemento radice e l'annidamento completo di un file Drill Plan (DRPPlan, GenHead, GenTrailer)?

### Takeaway
La radice è `DRPPlan` (namespace predefinito `http://www.iredes.org/xml/DrillRig`, prefisso `IR:` = `http://www.iredes.org/xml`), con dentro `IR:GenHead` → (`IR:SiteHead`) → `IR:PlanId` → (`IR:PlanName`, `IR:Comment`×0..8, `IR:Project`, `IR:WorkOrder`) → blocchi `DRPLrefData` / `PositionData` / `DrillPosPlan` / `DrillPlan` → `IR:GenTrailer` (`FileCloseDate` + `ChkSum`). `DrillPlan` contiene `NumberOfHoles` e 1..1000 `Hole` di tipo `DRholeType`. Lo schema pubblicato e i file reali divergono sulle versioni (schema: valori *fixed* "V 1.4"/"V 1.3"; file reali: "V 1.0", "V 1.2AC").

### Cited Findings

**Radice `DRPPlan` — [LETTO-PAGINA]**
- `DRPPlan`: Definition Type Element, namespace `http://www.iredes.org/xml/DrillRig`, tipo `IR:IRplanGenType`, schema contenitore `DrillRig.xsd`; documentazione: "IREDES Drill Rig Production Plan". — [iredes.org/irdocs/drpplan.html](https://iredes.org/irdocs/drpplan.html)
- Figli elencati nella tabella della pagina, in ordine: `GenHead` (IR:GenHead, 1..1), `SiteHead` (0..1), `PlanId` (IR:PlanId, 1..1), `PlanName` (0..1), `Comment` (0..8), `Project` (0..1), `WorkOrder` (0..1), `DRPLrefData` (1), `PositionData` (1), `DrillPosPlan` (1), `DrillPlan` (1), `GenTrailer` (IR:GenTrailer, 1). — [drpplan.html](https://iredes.org/irdocs/drpplan.html)
- **Divergenza tabella/codice sulla stessa pagina**: il codice XSD avvolge `DRPLrefData`, `PositionData`, `DrillPosPlan`, `DrillPlan` e `GenTrailer` in un `xsd:choice maxOccurs="unbounded"`, con l'annotazione "Please note that at least one of the following optional elements has to be covered by a DRPPLan data set". Quindi i quattro blocchi di contenuto non sono tutti obbligatori: ne basta uno. — [drpplan.html](https://iredes.org/irdocs/drpplan.html)
- Attributi della radice: `IRVersion` (IR:IRVersion, required), `IRDownwCompat` (IR:IRDownwCompat, required), `DRPPlanVersion` (required, fixed "V 1.3"), `DRPPlanDownwCompat` (required, fixed "V 1.3"). — [drpplan.html](https://iredes.org/irdocs/drpplan.html)
- Tipo base `IREDESType` (schema `IRtypes.xsd`, namespace `http://www.iredes.org/xml`): attributi `IRVersion` fixed "V 1.4" e `IRDownwCompat` fixed "V 1.3", figli `GenHead` 1..1 e `SiteHead` 0..1; documentazione "Base type IREDES complete Data Set". — [iredes.org/irdocs/iredestype.html](https://iredes.org/irdocs/iredestype.html)
- `DrillRig.xsd`: target namespace `http://www.iredes.org/xml/DrillRig`; include `./DRbaseClasses.xsd`; importa `../CuO/IRappBaseClasses.xsd`, `../CuO/IRtypes.xsd`, `../CuO/IRcoordNav.xsd` (namespace `http://www.iredes.org/xml`); la documentazione lo chiama "IREDES Drill rig XML schema version 1.3 proposal". Elementi globali visti (pagina letta fino a 100.000 caratteri su 114.975): `DRPPlan`, `DRPPerf`, `DRMaint`, `DRPQual`, `DRMWD`, `DRTunnelLine`, `DRLaserLine`, `HoleDeviation`, `DRContour`, `DRFixPoints`. — [iredes.org/irdocs/drillrig_xsd.html](https://iredes.org/irdocs/drillrig_xsd.html)
- `DRbaseClasses.xsd`: "IREDES Drill rig XML schema version 1.3"; tipi complessi `DRrefType`, `DRholeType`, `DRpositionType`, `DRboltType`; tipi semplici `DRBoomNum`, `DRHoleID`, `DRBoomID`, `DRDepthTag`. — [iredes.org/irdocs/drbaseclasses_xsd.html](https://iredes.org/irdocs/drbaseclasses_xsd.html)

**`GenHead` e `GenTrailer` — [LETTO-PAGINA]**
- `GenHead` (IRtypes.xsd, ns `http://www.iredes.org/xml`), "This is the General Header": `FileCreateDate` (xsd:dateTime, 1..1, "Date of file creation. This is the date/time stamp for initializatioin of the Data Set."), `IRversion` (1..1, valore fixed "V 1.4", con attributo `DownwCompat` required fixed "V 1.3"), `ProjectInfo` (0..1; figli `Signature` IRtext 0..1, `Comment` IRtextLong 0..1), `EquipmentInfo` (0..1; "ATTENTION: This information shall not be required to interpret a standard conformant data set."). — [iredes.org/irdocs/genhead.html](https://iredes.org/irdocs/genhead.html)
- **Attenzione alla grafia**: l'attributo della radice è `IRVersion` (V maiuscola), l'elemento dentro GenHead è `IR:IRversion` (v minuscola) con attributo `DownwCompat`. Confermato dall'esempio reale qui sotto.
- `GenTrailer` (tipo `IR:GenTrailerType`, IRtypes.xsd): `FileCloseDate` (1..1) e `ChkSum` (1..1); "The Trailer contains a checksum over all data in an IREDES file." — [iredes.org/irdocs/gentrailer.html](https://iredes.org/irdocs/gentrailer.html)

**Blocco `DrillPlan` — [LETTO-PAGINA]**
- `DrillPlan` ("Drill plan to be used when drilling at different positions."): `NumberOfHoles` (xsd:unsignedShort, 1..1, "Total number of holes in plan"), `Hole` (DRholeType, **1..1000**, "Hole data for specified hole"), `BoomSeq` (0..10; `BoomId` DRBoomID + `Sequence` 1..1000 con `SeqNum` ("Sequence number. Starting at 1."), `HoleId`, `EquipmentData` 0..1), `LineTable` (0..1; `Line` IR:IRlineType 1..1000), `EquipmentData` (IR:IRoptionType 0..1), `DrillBits` (0..1; annotazione nello schema: "TODO: This tag is not usable since some nodes lack type definitions."). — [drpplan.html](https://iredes.org/irdocs/drpplan.html)
- `DrillPosPlan`: elemento di tipo `IR:IRplanGenType` (quindi con i propri `GenHead` 1..1, `SiteHead`, `PlanId` 1..1, `PlanName`, `Comment` 0..8, `Project`, `WorkOrder` e gli attributi `IRVersion`/`IRDownwCompat` required), "Local position information. That is, position of the plan."; l'oggetto di reporting corrispondente è `DRPQual/PositionQuality`. — [iredes.org/irdocs/drillposplan.html](https://iredes.org/irdocs/drillposplan.html)
- `PositionData` è di tipo `DRpositionType`; `DRPLrefData` di tipo `DRrefType` ("Plan reference information: Matching Object for reporting: DRPQual/ReferenceData"). — [drpplan.html](https://iredes.org/irdocs/drpplan.html)

**`DRholeType` (il foro) — [LETTO-PAGINA]**
- Sequenza: `HoleId` (DRHoleID, 1..1), `HoleName` (IR:IRtextShort, 0..1), `StartPoint` (IR:IRpointType, 1..1), `EndPoint` (IR:IRpointType, 1..1), `TypeOfHole` (enumerazione su IRtextShort, 0..1), `DrillBitDia` (unsignedShort ≥0, 0..1, **mm**), `DrillBitType` (0..1: Button, Cross, Reaming, Others, Undefined), `RollAngle` (IR:IRangle, 0..1, gradi 0–360), `MwdOn` (xsd:boolean, 0..1: MWD atteso nel piano / eseguito nel log qualità), `HoleOptions` (IR:IRoptionType, 0..1). `TypeOfHole` ammette 16 valori (la pagina ne mostra tra gli altri Reference, CutHole, Casing, Probe, Grout, Spiling, Cleaning, Others, Undefined). — [iredes.org/irdocs/drholetype.html](https://iredes.org/irdocs/drholetype.html)
- `DRHoleID`: "Hole id code. To uniquely identify each hole in the plan." — [drbaseclasses_xsd.html](https://iredes.org/irdocs/drbaseclasses_xsd.html)
- L'elenco completo dei 16 `TypeOfHole` si ricava dalla documentazione del database Epiroc Surface Manager (tabella DrilledHole): "0 = Undefined, 1 = Reference, 2 = CutHole, 3= ReamingHole, 4 = EasersHole, 5 = BoltHole, 6 = InjectionHole, 7 = SecondContour, 8 = Bottom, 9 = Contour, 10 = Casing, 11 = Probe, 12 = Grout, 13 = Spiling, 14 = Cleaning, 15 = Others"; nella tabella PlannedHole Epiroc aggiunge "16 = Production" (estensione Epiroc, non nello schema 1.3). **[LETTO-FILE]** — [Surface Manager database.pdf nel repo GitHub brentbuffham/EPIROCSurfaceManager](https://github.com/brentbuffham/EPIROCSurfaceManager)

### Inferences
- Scheletro minimo plausibile per un piano di superficie (deduzione, da validare su un rig o su Surface Manager): radice `DRPPlan` con i due `xmlns` e gli attributi di versione; `IR:GenHead` (`IR:FileCreateDate`, `IR:IRversion DownwCompat=…`); `IR:PlanId`; opzionali `IR:PlanName`/`IR:Comment`/`IR:Project`/`IR:WorkOrder`; `DrillPlan` con `NumberOfHoles` + N×`Hole`; `IR:GenTrailer` (`IR:FileCloseDate`, `IR:ChkSum`). L'ordine dei figli è quello di una `xsd:sequence` ereditata da `IRplanGenType`, quindi va rispettato.
- Le versioni scritte nei file reali ("V 1.0" nel 2005 e nell'esempio Epiroc 2026, "V 1.2AC" su Atlas Copco 2016) **non coincidono** con i valori *fixed* della documentazione online (IRVersion "V 1.4", DRPPlanVersion "V 1.3"). Deduzione: gli importatori reali non validano contro l'XSD corrente e leggono per nome di elemento; scrivere "V 1.0" come Epiroc è la scelta più compatibile con i rig Epiroc, ma non è dimostrato che sia accettata ovunque.
- L'esempio Epiroc mostra sulla radice solo `IRVersion` (senza `IRDownwCompat`, `DRPPlanVersion`, `DRPPlanDownwCompat`, che lo schema dichiara *required*). Può essere una semplificazione del post: non è verificato su un file vero.
- `ExtendedHoleStatus` dentro `HoleOptions`/`opt:HoleData` è un'estensione Epiroc (il punto di estensione dello standard è `HoleOptions` di tipo `IR:IRoptionType`), non parte dello schema 1.3.
- `DrBitType` e `BitChange` citati dalla documentazione del database Epiroc come tag "in drill plan log"/"in DQ log" non corrispondono al nome di schema `DrillBitType`: i file Epiroc possono usare nomi di tag propri (deduzione dal solo documento del database).

## 2. Unità e convenzioni degli assi di PointX / PointY / PointZ; come le mappano le implementazioni reali

### Takeaway
Lo schema dice solo "UNIT: meter" e rimanda a un documento esterno ("IREDES coordinate system description") che non ho trovato. Nella pratica Epiroc (e chi scrive per Epiroc: Kirra, le query su Surface Manager) **`PointX` = Nord (Northing), `PointY` = Est (Easting), `PointZ` = quota verso l'alto**, cioè un sistema sinistrorso; Carlson offre un'opzione per scambiare X e Y in importazione — segno che la convenzione non è uniforme fra produttori.

### Cited Findings
- `IRpointType` (schema `IRcoordNav.xsd`, ns `http://www.iredes.org/xml`): `PointX`, `PointY`, `PointZ`, tutti `xsd:double`, default 0; "Point data type. Specifies one three dimensional point."; per ciascun asse: "Point x-coordinat. See definition in "IREDES coordinate system description" document. UNIT: meter" (idem y, Z). **[LETTO-PAGINA]** — [iredes.org/irdocs/irpointtype.html](https://iredes.org/irdocs/irpointtype.html)
- `IRcoordSysType` (IRcoordNav.xsd): `CoordSysName` (IRtextShort, 1..1), `TMatrix` (IR4x4matrix, 1..1, "4x4 matrix to describe how to transform from parent to child coordinate system."), `CsysType` (stringa di lunghezza 1, enumerazione `L` / `R`: "Type of the Coordinate System: L= Left handed R= Right handed. To be used for explanatory reasons."), `ChildCSys` (ricorsivo, 0..10); a livello di tipo: "Right hand system is assumed." **[LETTO-PAGINA]** — [iredes.org/irdocs/ircoordsystype.html](https://iredes.org/irdocs/ircoordsystype.html)
- `DRpositionType` (DRbaseClasses.xsd): `PositionId` (0..1), `PositionName` (0..1), `CoordSystem` (IR:IRcoordSysType, **1..1**), `PlanIdRef` (IR:IRtext, **1..1**: "The string "VOID" has to be used if no plan has been used."), `PosComment` (0..1), `LineIdRef` (0..1), `Bearing` (IR:IRangle, 0..1: "Drill plan bearing to geografic north (bearing = 0). This element gives the logical blast direction. Unit: degrees"), `EquipmentData` (0..1). Usato da `PositionData` (piano), `PositionQuality` (qualità/MWD), `PositionInfo` (HoleDeviation). **[LETTO-PAGINA]** — [iredes.org/irdocs/drpositiontype.html](https://iredes.org/irdocs/drpositiontype.html)

(riguarda il formato testo/CSV che Surface Manager converte in IREDES). **[LETTO-FILE]** — [SurfaceManager.en.pdf nel repo brentbuffham/EPIROCSurfaceManager](https://github.com/brentbuffham/EPIROCSurfaceManager)

## 3. Come si calcola il checksum (ChkSum / CRC32) nel GenTrailer e gli importatori lo impongono?

### Takeaway
Lo standard dichiara CRC32 sull'intero file XML pronto all'invio, calcolato con la stringa "0" al posto del valore, tipo `xsd:hexBinary`. L'autore di Kirra afferma invece — verificato a suo dire su 10 file reali di Epiroc Surface Manager — che il segnaposto giusto è il tag **vuoto**, non "0", e nel suo esempio il valore è scritto in **decimale**. I due file reali di rig che ho visto (2005 e Atlas Copco 2016) portano `<IR:ChkSum>0</IR:ChkSum>`: il checksum di fatto non è sempre calcolato.

### Cited Findings
- `ChkSum`: Element, ns `http://www.iredes.org/xml`, tipo `xsd:hexBinary`, schema `IRtypes.xsd`, 1..1. Documentazione (citazioni brevi): "Check sum including all data Objects in the Data Set"; "Checksum is calculated over the ENTIRE XML file ready to send"; "using the value string "0" as ChkSum value"; "After calculating the checksum the resulting value is written into the ChkSum tag"; "Interpretation is done in reverse order also using "0" as a defined value"; "The algorithm is: CRC32". **[LETTO-PAGINA]** — [iredes.org/irdocs/chksum.html](https://iredes.org/irdocs/chksum.html)
- File d'esempio IREDES 2005: `<IR:ChkSum>0</IR:ChkSum>`. **[LETTO-FILE]** — [apcom05-presentation.pdf](https://iredes.org/wp-content/uploads/2019/04/apcom05-presentation.pdf)
- File MWD reale Atlas Copco Boomer (RCS 5.3.2, 2016): `IR:ChkSum` = `0`. **[LETTO-PAGINA]** — [MATLAB Answers 312070](https://www.mathworks.com/matlabcentral/answers/312070-how-to-import-xml-iredes-file-format-with-measurement-while-drilling-data-from-tunnel-drill-rigs-in)
- Post dell'autore di Kirra (citazioni): "IREDES files include a CRC32 checksum for data integrity."; "Generate the complete XML with **empty** as placeholder"; "Calculate CRC32 over the entire XML string (UTF-8, preserving `\r\n` line endings)"; "Replace the empty tag content with the calculated checksum"; "The critical insight is that the placeholder must be **empty** — not `"0"`."; "Using `0` as the placeholder produces the wrong CRC32."; "Verified against 10 real files."; nei commenti del codice: "// 3. Insert result as decimal (or uppercase hex for HEXBINARY)" e "// 4. Compare with original (decimal or hex)". Variante CRC descritta: CRC32 standard (polinomio riflesso 0xEDB88320, valore iniziale 0xFFFFFFFF, XOR finale 0xFFFFFFFF), intero senza segno a 32 bit. Valore nell'esempio: `<IR:ChkSum>2847593621</IR:ChkSum>` (decimale). **[LETTO-PAGINA]** — [buymeacoffee.com/brentbuffham/iredes](https://buymeacoffee.com/brentbuffham/iredes)
- Lo stesso post contiene anche la frase "I still haven't cracked the Checksum issues." e la dicitura "SOLVED (April 2026)" posteriore alla data del post (25/01/2026): la pagina è stata aggiornata e contiene due stati del problema. **[LETTO-PAGINA]** — [buymeacoffee.com/brentbuffham/iredes](https://buymeacoffee.com/brentbuffham/iredes)
- Raccomandazione dell'autore in lettura: validare il checksum e **avvisare** in caso di errore invece di rifiutare, perché i file possono essere stati modificati a mano. **[LETTO-PAGINA]** (riassunto) — [buymeacoffee.com/brentbuffham/iredes](https://buymeacoffee.com/brentbuffham/iredes)

### Inferences
- **Conflitto fra fonti, non risolto**: standard = segnaposto "0" + hexBinary; pratica Epiroc secondo Buffham = segnaposto vuoto + decimale. Non ho modo di verificare nessuna delle due su un file reale con checksum diverso da zero. Chi implementa dovrebbe: in scrittura rendere selezionabile il segnaposto e il formato; in lettura provare entrambe le varianti (vuoto/"0", decimale/esadecimale) e non rifiutare mai un file per il solo checksum.
- Il fatto che un Atlas Copco Boomer e l'esempio ufficiale scrivano `0` indica che almeno alcuni lettori non impongono il checksum (deduzione: se lo imponessero, i file dei rig stessi sarebbero rifiutati). Non ho trovato nessuna fonte che dica che un rig **rifiuta** un piano con checksum errato o a zero.
- Il calcolo dipende da dettagli di serializzazione (codifica UTF-8, fine riga `\r\n`, presenza di BOM): qualunque riformattazione dell'XML dopo il calcolo lo invalida.

### Gaps
- Nessuna documentazione di Epiroc, Sandvik, Trimble, Carlson, Maptek dichiara se il checksum viene verificato in importazione.
- Non verificato se i rig Epiroc di superficie accettino `<IR:ChkSum>0</IR:ChkSum>` in un `DRPPlan`.
- La tabella dei formati del checksum nel post di Buffham è un'immagine, non letta.

## 5. Esiste un profilo IREDES per il piano di caricamento/innesco (Charger) ed è usato da software di superficie?

### Takeaway
Esiste un profilo **Charger** (namespace `http://www.iredes.org/xml/Charger`, schema `IRChargers.xsd`) con una radice `ECChargeHole` che descrive per foro detonatori (tipo, ritardo), booster, esplosivi (massa, lunghezza, tratto), borraggio e camere d'aria, più radici di reporting (`ECPQual`, `ECPPerf`, `ECShotData`). Non ho trovato **nessun** software di brillamento a cielo aperto che dichiari di importarlo o esportarlo, né un file d'esempio.

### Cited Findings
- Nell'albero di derivazione di `IREDESType` compaiono, col prefisso `nsB` (namespace Charger): `nsB:ECShotData` (sotto `IR:IREventGenType`), `nsB:ECPPerf` (sotto `IR:IRpPerfGenType`), `nsB:ECPQual` (sotto `IR:IRpQualGenType`), `nsB:ECChargeHole` (derivato direttamente da `IREDESType`). Sotto `IR:IRplanGenType` (i "piani") ci sono solo elementi DrillRig (`DRContour`, `DRFixPoints`, `DRLaserLine`, `DRPPlan`, `DrillPosPlan`, `DRTunnelLine`) e `LT:IRLTPlan` (LHD/camion): **nessun piano del Charger**. **[LETTO-PAGINA]** — [iredes.org/irdocs/iredestype.html](https://iredes.org/irdocs/iredestype.html)
- `ECChargeHole`: Element, namespace `http://www.iredes.org/xml/Charger`, tipo `IR:IREDESType`, schema `IRChargers.xsd`; figli `GenHead` (1), `SiteHead` (0..1), `Hole` (**1..1000**, tipo anonimo che estende `ECholeType`, "Hole data for specified hole"). Dentro `Hole`: `Detonator` (1..10: `Type` ∈ {Electric, Non-Electric, Electronic}, `Manufacturer`, `PartNo`, `ProductText`, `SerialNo`, `Delay` xsd:duration "Detonation delay in msec.", `LocationInHole` float in metri dall'inizio foro, "Start of the hole at real rock contact (0 position)."), `Booster` (1..10: `Type`, `Manufacturer`, `PartNo`, `ProductText`, `SerialNo`, `PrimerType`, `AmountUsed`, `LocationInHole`), `TypeOfExplosives` (1..n: `Manufacturer`, `ProductID`, `DeliveryID`, `ProductText`, `StartPoint`, `EndPoint`, `MassOfExplosives` "Total amount of explosives per hole (in kilograms)", `LengthOfExplosives`, `Type` ∈ {bulk, pumped, packaged}, `Recipe` ECRecipe 0..1), `Lid` (float, "Collar length in meters"), `Stemming` (0..10: `StartPoint`, `EndPoint`), `AirDeck` (0..10: `StartPoint`, `EndPoint`), `ChargeMode` ∈ {Manual, Automatic}, `ChargingSequence` (0..10: `ChargerID`, `Sequence` 1..1000 con `SeqNum`, `HoleID`, `EquipmentData`), `HoleEvents` (`Depth`, `Comments` ∈ {Water in the hole, Hole blocked}; "Should be identical to the similar drill rigs reporting."), `Comments`. **[LETTO-PAGINA]** — [iredes.org/irdocs/ecchargehole.html](https://iredes.org/irdocs/ecchargehole.html)
- `ECPQual` ("IREDES Charging Performance Reporting", tipo `IR:IRpQualGenType`, IRChargers.xsd): testata di report come DRPQual (`ReportId`, `StartLogTime`, `EndLogTime`, `PlanIdRef`…), poi `ExplosiveMaterial` (1..n: `Delivery` con `DeliveryID`/`TimeAtFace`/`TimeFinished`, `Mass` "Mass of material in kilograms.", `ProductCode`, `Type`, `CupTest` con `CupVolume`, `Density` in g/cm^3, `Temperature` in °C, `Timestamp`, `Operator`) e `Calibration` (`CalibrationDate`, `NextCalibrationDue`, `Operator`). Curiosità dello schema: gli attributi di versione si chiamano `DRPQualVersion`/`DRPQualDownwCompat` (fixed "V 1.3") anche qui, e un'annotazione dice "Type from ECRealHole to add". **[LETTO-PAGINA]** — [iredes.org/irdocs/ecpqual.html](https://iredes.org/irdocs/ecpqual.html)

### Inferences
- `ECChargeHole` deriva da `IREDESType` e non da `IRplanGenType`, ha molti campi obbligatori di tracciabilità (`SerialNo`, `DeliveryID`) e riferimenti a "real rock contact": ha la forma di un **consuntivo per foro** (che cosa è stato caricato) più che di un piano di caricamento da inviare a un'unità di carica. È una deduzione dalla struttura, non una dichiarazione dello standard.
- Il profilo Charger è nato per il caricamento meccanizzato in sotterraneo (contesto della presentazione 2005, elementi come `ChargingLine`, `TimeAtFace`). Per il cielo aperto lo scambio del piano di carica/innesco passa di fatto per formati dei produttori di esplosivi e detonatori elettronici; non ho trovato alcun software di superficie che citi il profilo Charger IREDES.
- Lo schema Charger appare meno rifinito del DrillRig (attributi di versione copiati col nome `DRPQual…`, annotazioni "to add"): rischio di implementare su una base instabile.

### Gaps
- Nessun file d'esempio del profilo Charger trovato; nessuna pagina di prodotto (Orica, Dyno, MAXAM, Epiroc, Normet, BME, ecc.) letta che dichiari supporto IREDES Charger.
- `ECholeType` (il tipo base del foro del Charger: identificativo, coordinate?) e `ECRecipe` non letti: non so se il foro del Charger porta coordinate o solo un `HoleID` di aggancio al Drill Plan.
- Versione corrente del profilo Charger e suo stato di manutenzione: non trovati.
